# Stage.03-2 - Idempotency and Transactionality

> 💡 **Further reading:** for a detailed analysis of the architectural patterns, with diagrams and examples, see [`Stage.03-Architectural-Patterns.md`](Stage.03-Architectural-Patterns.md)

## 🎯 Stage Goal

Implement **idempotency** in command processing and guarantee **transactional consistency** between stored integration events and domain operations, ensuring:

- Commands are processed only once (duplicate prevention)
- Integration events are stored within database transactions
- The domain state and the events table stay consistent
- The system is resilient to retries and network failures

---

## 🎨 Implemented Architectural Patterns

> This section summarizes the patterns. For detailed explanations, specific problems and flow diagrams, see [`Stage.03-Architectural-Patterns.md`](Stage.03-Architectural-Patterns.md)

### 1. **Transactional Outbox Pattern**

**Problem:**
- Integration events could be published to RabbitMQ before the DB transaction commits
- If the transaction fails after publishing, other services receive events about operations that never happened
- The domain state and the published messages become inconsistent

**Solution:**
Store the events in a table (`IntegrationEventLog`) **within the same transaction** as the domain entities. Publish them to the message broker after a successful commit.

**Implementation:**
```csharp
// 1. Save the event within the transaction
await _accountIntegrationEventService.AddAndSaveEventAsync(integrationEvent);
// ← Event saved in IntegrationEventLog (same transaction)

// 2. Commit the transaction
await _dbContext.CommitTransactionAsync(transaction);

// 3. Publish events only if the commit succeeded
await _accountIntegrationEventService.PublishEventsThroughEventBusAsync(transactionId);
```

**Guarantees:**
- ✅ **Atomicity**: domain + events are saved, or fail, together
- ✅ **Consistency**: the DB state always matches the saved events
- ✅ **No phantom events**: only events from committed transactions are published
- ⚠️ **No publish retry**: if RabbitMQ fails, the event stays as `PublishedFailed` in the table; republishing it would require a background process (not implemented)

### 2. **Idempotent Consumer/Processor Pattern**

**Problem:**
- Clients may send the same command several times (timeouts, retries, network errors)
- Without protection, duplicate records are created or operations run more than once
- Unwanted side effects (duplicate charges, repeated emails, etc.)

**Solution:**
Each command carries a **unique request ID** generated by the client. The server checks whether that ID has already been processed before running the business logic.

**Implementation:**
```csharp
// The client generates a unique ID
var requestId = Guid.NewGuid();
var command = new IdentifiedCommand<CreateOrganizationCommand, bool>(
    new CreateOrganizationCommand(...), 
    requestId
);

// IdentifiedCommandHandler checks for duplicates
var alreadyExists = await _requestManager.ExistAsync(message.Id);
if (alreadyExists)
{
    return CreateResultForDuplicateRequest(); // ← Returns without processing
}

// Register the request ID
await _requestManager.CreateRequestForCommandAsync<T>(message.Id);

// Process the command
var result = await _mediator.Send(message.Command, cancellationToken);
```

**Guarantees:**
- ✅ **One execution per request ID**: the same `x-requestid` never runs the command again
- ✅ **Idempotency**: several calls with the same ID → same result
- ✅ **No duplicate side effects**: expensive operations are not repeated

### 3. **Unit of Work Pattern (implicit)**

**Problem:**
- Several DB operations must run as one atomic unit
- Commit/rollback of all of them has to be coordinated
- Managing transactions by hand is error-prone

**Solution:**
`TransactionBehavior` acts as the unit of work, wrapping the whole command execution in a database transaction.

**Implementation:**
```csharp
public class TransactionBehavior<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse>
{
    public async Task<TResponse> Handle(TRequest request, RequestHandlerDelegate<TResponse> next, ...)
    {
        // Begin transaction
        await using var transaction = await _dbContext.BeginTransactionAsync();

        // Run the command (may change several aggregates)
        var response = await next();

        // Commit every change
        await _dbContext.CommitTransactionAsync(transaction);

        // Publish events only if the commit succeeded
        await _accountIntegrationEventService.PublishEventsThroughEventBusAsync(transactionId);

        return response;
    }
}
```

**Guarantees:**
- ✅ **Atomicity**: all operations or none
- ✅ **Centralized management**: transaction logic lives outside the handler
- ✅ **Ready for retries**: runs the transaction inside an `ExecutionStrategy` (actual retries need `EnableRetryOnFailure`, enabled later)

### 4. **Pipeline Behavior Pattern**

**Problem:**
- Cross-cutting concerns (logging, transactions, validation) scattered across handlers
- Duplicated cross-cutting code
- Hard to keep common concerns consistent

**Solution:**
MediatR pipeline behaviors intercept commands and add cross-cutting functionality declaratively.

**Implementation:**
```csharp
services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssemblyContaining(typeof(Program));
    cfg.AddOpenBehavior(typeof(LoggingBehavior<,>));        // ← 1st: log in/out
    cfg.AddOpenBehavior(typeof(TransactionBehavior<,>));    // ← 2nd: transactional wrapper
});
```

**Execution flow:**
```
Request → LoggingBehavior → TransactionBehavior → CommandHandler → Response
```

**Guarantees:**
- ✅ **Separation of concerns**: handlers only contain business logic
- ✅ **Reusability**: behaviors apply to every command
- ✅ **Controlled order**: the pipeline runs behaviors in registration order

---

### 5. **Eventual Consistency Pattern**

**Problem:**
- Distributed operations cannot be atomic (CAP theorem)
- Distributed transactions (2PC) are slow and complex
- Services still need to stay consistent with each other

**Solution:**
Accept that the system is **temporarily inconsistent** until integration events are published and processed by other services.

**Implementation:**
```
1. Command runs → Organization created in the DB
2. Event saved in IntegrationEventLog (same transaction)
3. Transaction commit
4. Event published to RabbitMQ
5. Other services process the event (eventual consistency)
```

**Guarantees:**
- ✅ **Eventual consistency**: the system converges to a consistent state
- ✅ **Decoupling**: services don't need to be available synchronously
- ✅ **Scalability**: events are processed asynchronously

## 🏗️ Architectural Decisions

### Why idempotency?

In distributed systems, duplicate requests are unavoidable because of:

- Client retries after timeouts
- Load balancers replaying requests
- Processing failures
- Network glitches

Idempotency guarantees that **processing the same command several times has the same result** as processing it once.

### Why a transaction behavior?

To avoid **inconsistencies** between:
- The persisted domain state (aggregates)
- The stored integration events

Both must happen in the **same database transaction**, or neither is persisted.

### 2. **AccountIntegrationEventService**

Service that **coordinates** storing and publishing integration events.

**Responsibilities:**

1. **Save events within the domain transaction** (`AddAndSaveEventAsync`)
2. **Publish pending events after the commit** (`PublishEventsThroughEventBusAsync`)

**Implementation:**

```csharp
public class AccountIntegrationEventService : IAccountIntegrationEventService
{
    private readonly IEventBus _eventBus;
    private readonly AccountContext _accountContext;
    private readonly IIntegrationEventLogService _eventLogService;
    private readonly ILogger<AccountIntegrationEventService> _logger;

    public async Task AddAndSaveEventAsync(IntegrationEvent evt)
    {
        _logger.LogInformation("Enqueuing integration event {IntegrationEventId}", evt.Id);
        
        // Saves the event in the SAME transaction as the domain changes
        await _eventLogService.SaveEventAsync(evt, _accountContext.GetCurrentTransaction());
    }

    public async Task PublishEventsThroughEventBusAsync(Guid transactionId)
    {
        var pendingLogEvents = await _eventLogService
            .RetrieveEventLogsPendingToPublishAsync(transactionId);

        foreach (var logEvt in pendingLogEvents)
        {
            try
            {
                await _eventLogService.MarkEventAsInProgressAsync(logEvt.EventId);
                await _eventBus.PublishAsync(logEvt.IntegrationEvent);
                await _eventLogService.MarkEventAsPublishedAsync(logEvt.EventId);
            }
            catch (Exception ex)
            {
                await _eventLogService.MarkEventAsFailedAsync(logEvt.EventId);
            }
        }
    }
}
```

**Flow:**
1. The domain event handler calls `AddAndSaveEventAsync`
2. The event is saved in the `IntegrationEventLog` table with state `NotPublished`
3. After the commit, `TransactionBehavior` calls `PublishEventsThroughEventBusAsync`
4. Events are marked `InProgress`, published, and marked `Published`

### 3. **TransactionBehavior** (MediatR pipeline)

Behavior that **wraps commands in transactions** and ensures integration events are published only if the transaction succeeded.

**Implementation:**

```csharp
public class TransactionBehavior<TRequest, TResponse> : IPipelineBehavior<TRequest, TResponse> 
    where TRequest : IRequest<TResponse>
{
    private readonly AccountContext _dbContext;
    private readonly IAccountIntegrationEventService _accountIntegrationEventService;
    private readonly ILogger<TransactionBehavior<TRequest, TResponse>> _logger;

    public async Task<TResponse> Handle(
        TRequest request, 
        RequestHandlerDelegate<TResponse> next, 
        CancellationToken cancellationToken)
    {
        if (_dbContext.HasActiveTransaction)
        {
            return await next();  // A transaction is already active, don't create another
        }

        var strategy = _dbContext.Database.CreateExecutionStrategy();

        return await strategy.ExecuteAsync(async () =>
        {
            Guid transactionId;

            await using var transaction = await _dbContext.BeginTransactionAsync();
            
            _logger.LogInformation("Begin transaction {TransactionId}", transaction.TransactionId);

            var response = await next();  // Runs the handler

            _logger.LogInformation("Commit transaction {TransactionId}", transaction.TransactionId);

            await _dbContext.CommitTransactionAsync(transaction);
            transactionId = transaction.TransactionId;

            // Publish events AFTER the commit
            await _accountIntegrationEventService.PublishEventsThroughEventBusAsync(transactionId);

            return response;
        });
    }
}
```

**Characteristics:**

- ✅ Uses an `ExecutionStrategy`, required to combine explicit transactions with retries. At this stage the `DbContext` has no `EnableRetryOnFailure`, so the strategy **doesn't retry yet**; it's enabled later (Identity in Stage.03-4, Accounts after Stage.04)
- ✅ Integration events are published **only if the commit succeeds**
- ✅ Structured logging with `TransactionId`
- ✅ No nested transactions

**DI registration:**

```csharp
services.AddMediatR(cfg =>
{
    cfg.RegisterServicesFromAssemblyContaining(typeof(Program));
    cfg.AddOpenBehavior(typeof(LoggingBehavior<,>));
    cfg.AddOpenBehavior(typeof(TransactionBehavior<,>));  // ← Runs after LoggingBehavior
});
```

### 4. **Idempotency with IdentifiedCommand**

Generic command wrapper that carries a unique **request ID**.

**IdentifiedCommand:**

```csharp
public class IdentifiedCommand<T, R> : IRequest<R>
    where T : IRequest<R>
{
    public T Command { get; }
    public Guid Id { get; }  // Request ID used to detect duplicates
    
    public IdentifiedCommand(T command, Guid id)
    {
        Command = command;
        Id = id;
    }
}
```

**IdentifiedCommandHandler:**

```csharp
public abstract class IdentifiedCommandHandler<T, R> : IRequestHandler<IdentifiedCommand<T, R>, R>
    where T : IRequest<R>
{
    private readonly IMediator _mediator;
    private readonly IRequestManager _requestManager;
    private readonly ILogger<IdentifiedCommandHandler<T, R>> _logger;

    public async Task<R> Handle(IdentifiedCommand<T, R> message, CancellationToken cancellationToken)
    {
        var alreadyExists = await _requestManager.ExistAsync(message.Id);
        
        if (alreadyExists)
        {
            return CreateResultForDuplicateRequest();  // Command already processed
        }

        // Register the request ID in the database
        await _requestManager.CreateRequestForCommandAsync<T>(message.Id);

        // Send the real command to its handler
        var result = await _mediator.Send(message.Command, cancellationToken);

        return result;
    }

    protected abstract R CreateResultForDuplicateRequest();
}
```

**CreateOrganizationIdentifiedCommandHandler:**

```csharp
public class CreateOrganizationIdentifiedCommandHandler 
    : IdentifiedCommandHandler<CreateOrganizationCommand, bool>
{
    public CreateOrganizationIdentifiedCommandHandler(
        IMediator mediator,
        IRequestManager requestManager,
        ILogger<IdentifiedCommandHandler<CreateOrganizationCommand, bool>> logger)
        : base(mediator, requestManager, logger)
    {
    }

    protected override bool CreateResultForDuplicateRequest()
    {
        return true;  // Duplicate requests return success
    }
}
```

**ClientRequestConfiguration:**

```csharp
public class ClientRequestConfiguration : IEntityTypeConfiguration<ClientRequest>
{
    public void Configure(EntityTypeBuilder<ClientRequest> requestConfiguration)
    {
        requestConfiguration.ToTable("requests");
        requestConfiguration.HasKey(r => r.Id);
        requestConfiguration.HasIndex(r => r.Id).IsUnique();  // ← Guarantees uniqueness
    }

```

**RequestManager:**

```csharp
public class RequestManager : IRequestManager
{
    private readonly AccountContext _context;

    public async Task<bool> ExistAsync(Guid id)
    {
        var request = await _context.FindAsync<ClientRequest>(id);
        return request != null;
    }

    public async Task CreateRequestForCommandAsync<T>(Guid id)
    {
        var exists = await ExistAsync(id);

        if (exists)
            throw new AccountDomainException($"Request with {id} already exists");

        var request = new ClientRequest()
        {
            Id = id,
            Name = typeof(T).Name,
            Time = DateTime.UtcNow
        };

        _context.Add(request);
        await _context.SaveChangesAsync();
    }
}
```

**Note:** in production, handle `DbUpdateException` for unique constraint violations.

## 📐 End-to-End Flow

### Command processing with idempotency

```
1. PUT /api/accounts with the x-requestid header → the endpoint creates IdentifiedCommand<CreateOrganizationCommand>
   ↓
2. TransactionBehavior (on the IdentifiedCommand) begins the transaction
   ↓
3. IdentifiedCommandHandler checks whether the request ID exists
   ↓
4a. If it exists → returns CreateResultForDuplicateRequest() (idempotency)
   ↓
4b. If not → saves the request ID (inside the transaction) and sends the inner command
   ↓
5. TransactionBehavior (on CreateOrganizationCommand) sees the active transaction and doesn't open another one
   ↓
6. CreateOrganizationCommandHandler creates the Organization
   ↓
7. SaveEntitiesAsync dispatches OrganizationCreatedDomainEvent
   ↓
8. The domain event handler calls AddAndSaveEventAsync → IntegrationEventLog (same transaction)
   ↓
9. TransactionBehavior COMMITs (request ID + Organization + event, all together)
   ↓
10. PublishEventsThroughEventBusAsync publishes to RabbitMQ and marks the event as Published
```

Because the request ID is saved within the same transaction, it is rolled back too if the command fails, and the client can retry with the same `x-requestid`.

## 🚀 Next Steps

### Stage.03-3 - Idempotent event handlers

So far idempotency is only implemented in **command processing** (application layer). The next step is idempotency when **consuming integration events**:

**Problem:**
- An integration event may be received several times (at-least-once delivery)
- Event handlers could process the same event more than once
- Event processing must be idempotent

**Planned solution:**
- Store processed event IDs in a deduplication table
- Check for duplicates before processing events
- Process events transactionally

### Later stages

With full idempotency (commands + events), the system is ready for:

- **Stage.03-4:** Resilient transactions in the integration handlers
- **Background workers** to retry failed events
- More sophisticated **retry policies** with Polly
- **Distributed transactions** with the Saga pattern
- **Compensating transactions** for distributed rollback
